## PRD에 보통 들어가는 것

| 영역 | 역할 |
|------|------|
| **문서 성격** | 무엇의 PRD인지, 다른 문서(스펙·테스트·설계)와의 관계 |
| **제품 개요** | 비전·Epic, 해결하려는 문제, 왜 이 도구/범위인지 |
| **범위** | In / Out of scope, 관련 문서 맵·single source of truth |
| **사용자** | 페르소나, 여정(고수준), 성공이 무엇인지 |
| **요구사항** | 기능(유저 스토리·AC), 도메인 규칙(Invariant), 비기능(NFR) |

| **검증·리스크** | BDD/Gherkin 요약, 알려진 갭·오픈 이슈 |
| **부록** | 용어, 원천 문서 인덱스, 버전·날짜 |

## 현재 `PRD.md`와의 대응

문서 앞부분에 적어두신 대로, **구현 세부를 대신하기보다 목표·범위·계약·성공 기준**을 모아 두는 형태로 잘 맞춰져 있습니다.

- **§1** → 비전, 문제 정식화, 4×4·TDD 선택 이유  
- **§2** → In/Out, Report 레벨 맵  
- **§3** → 페르소나·여정  
- **§4~5** → Invariant, User Stories  
- **§6** → ECB, 계약·컴포넌트·코딩 규칙  
- **§7~9** → BDD, NFR, Level 5 갭·이슈  
- **§10~11** → 용어, 원천 인덱스  

즉, **“무엇을 왜 만들고, 무엇까지 하며, 무엇과 어떻게 맞출지”**가 한 번에 읽히도록 구성되어 있습니다.

## 새로 쓰거나 보강할 때 고려할 만한 것

필수는 아니고, **팀·학습 프로젝트 성격**에 맞게 선택하면 됩니다.

1. **성공 지표 (KPI)** — 예: “Invariant 대비 테스트 추적률”, “커버리지 하한 달성”처럼 **측정 가능한 한두 줄**  
2. **마일스톤 / 우선순위** — US-01→… 의존은 있음; **릴리스·스프린트 단위**가 필요하면 표로  
3. **의존성·환경** — Python 3.10+ 등은 §6에 있음; **외부 서비스 없음** 같은 한 줄이 있으면 범위가 더 분명해짐  
4. **변경 이력** — 문서 버전·주요 개정일(지금은 **최종 정리: 2026-04-27** 한 줄)  
5. **승인** — §9에 Sign-off 언급이 있음; **누가·언제 승인**할지는 선택 사항  

---

**요약:** PRD에는 보통 **개요·범위·사용자·기능·비기능·아키텍처·검증·용어·참조**가 들어가고, 지금 파일은 그 틀을 이미 채우고 있습니다. 추가로 넣는다면 **성공 지표·일정/우선순위·변경 이력** 정도를 보완하는 수준이면 충분합니다.

## 잘 맞는 이유

1. **트랙 분리**  
   - **UI 트랙:** 화면에 보이는 것(에러 문구, 버튼 활성, 로딩) — **UX Contract**로 RED.  
   - **로직 트랙:** 도메인·유스케이스·검증 — **Logic Rule**로 RED.  
   MLOps에서도 “사용자에게 무엇을 보여줄지”와 “모델·데이터·추론이 무엇을 허용·거부·반환하는지”는 원래 다른 축입니다.

2. **MLOps를 어디에 두면 좋은지**  
   - **Logic 쪽에 가깝게:** 입력 스키마, 전처리 불변조건, 출력 스키마, 임계값·거부 규칙, 버전 호환(모델 ID·아티팩트 해시).  
   - **Boundary + 인프라:** 추론 클라이언트, 배포 파이프라인, 메트릭·로그 — 여기서는 “계약 테스트”와 “스모크/회귀”가 많습니다.  
   - **UI:** 추론 결과를 어떻게 표시할지(신뢰도, 경고, 재시도 UX)는 UX Contract로 고정.

3. **두 번째 슬라이드의 매핑 표**  
   시나리오마다 **UX Contract 열**과 **Logic Rule 열**을 같이 두는 방식은 PRD·테스트 설계·추적성에 그대로 쓸 수 있습니다. “결정(Decision)이 있는 문장만 테스트로 옮긴다”는 원칙도 TDD와 잘 맞습니다.

---

## 조심할 점 (MLOps 특유)

| 이슈 | 실무적 대응 |
|------|-------------|
| **비결정성** | 같은 입력에도 미세한 차이가 나면 “Logic RED”가 흔들립니다. **고정 시드**, **스냅샷 대신 불변조건**(스키마·범위·임계값), **회귀용 작은 골든 세트**를 Logic 계약에 넣는 편이 안전합니다. |
| **경계가 두 개** | UI ↔ API ↔ 모델 서빙이면 “듀얼”이 아니라 레이어가 늘어납니다. 슬라이드처럼 **사용자 관점 트랙** vs **도메인·ML 규칙 트랙**만 유지하고, **모델 서버는 Logic의 일부(또는 Boundary 구현)**로 묶어 두면 설계가 단순해집니다. |
| **데이터 드리프트** | Logic Rule에 “항상 같은 예측”만 걸면 깨지기 쉽습니다. **운영 메트릭**(드리프트 알림)은 TDD의 단위 테스트가 아니라 **모니터링·계약 테스트(스키마·SLA)** 쪽에 두는 게 맞습니다. |

---

## 기존 Magic Square PRD와의 정리

지금 `PRD.md`는 **GUI Out of Scope**, Dual-Track을 **Contract vs Algorithm**으로만 잡고 있습니다. **UI + MLOps**로 가면 PRD에 예를 들어 다음이 추가·갱신되는 편이 자연스럽습니다.

- **In Scope:** 웹/앱 경계, UX Contract 어휘(Visible/Active 등)  
- **Logic / MLOps:** 모델 입출력 계약, 에러 코드, 재시도·타임아웃, 모델 버전  
- **비기능:** 지연 시간, 가용성, PII/로깅 정책  
- **검증:** UI RTL/Playwright 등, Logic은 pytest + **모델 mock** 또는 **스테이징 아티팩트**로 고정

---

**한 줄로:** 슬라이드의 **“UI는 디자인으로 RED, 로직은 규칙으로 RED, 둘은 서로 모른다”**는 MLOps에도 그대로 이어지고, MLOps만 **불변조건·버전·비결정성**을 Logic 계약에 명시적으로 넣으면 됩니다. 원하시면 다음 단계로, **지금 레포 기준으로 “§6 Dual-Track”을 UI+Logic+MLOps 삼단으로 PRD에 붙이는 초안 목차**만 짧게 잡아 드리겠습니다.

# MagicSquare PRD — Dual-Track UI · Logic · MLOps 정리본

**문서 성격·원천**  
- 구현 전체 스펙이 아니라 **목표·범위·계약·성공 기준**의 한 장 요약. 상세 ID·스냅샷은 `Report/*.md`가 정본. (기존 서문)

---

## A. 제품 개요 (§1)

| 축 | 내용 |
|----|------|
| **비전** | Invariant 기반 사고 훈련; 4×4 마방진으로 규정 분해·명명·누락 없는 적용, ECB·계약 명확화 훈련. |
| **문제 정식** | “만든다”만이 아니라 (1) 규칙 만족 **판정**을 반복 가능하게 두고, (2) “해를 찾는 절차”는 종료·중간 의미를 **먼저** 약속. |
| **4×4·TDD 이유** | 기존 §1.3·§1.4와 동일 (탐색 의미, 재현성·계약·RED 의미). |

---

## B. 범위 — 세 트랙과의 관계 (§2)

| 구분 | 내용 |
|------|------|
| **In Scope** | 도메인·INV·입력 검증·판정·2-blank 완성, ECB, **경계 입출력(현재는 CLI 중심)**, pytest·커버 하한, `.cursorrules` TDD. |
| **Out of Scope (원문)** | GUI/Web UI, DB 영속(학습용은 InMemory 옵션), 5×5+, 분산·비동기. |
| **Dual-Track + MLOps 정리** | **UI 트랙**을 도입하면 Out of Scope의 “GUI”는 **범위 갱신** 대상이 됨. **MLOps**는 현재 Epic에 **학습용 숫자 퍼즐만** 있으면 “모델 추론” 항목은 없고, 확장 시 **Logic/MLOps 계약**으로 추가하는 식이 자연스럽다. |
| **문서 맵** | Level 1~5·`Prompting` — 기존 §2.3·§11과 동일. |

---

## C. 사용자·성공 정의 (§3)

- 페르소나·불안·성공: 학습자, TDD/ECB 맥락 — **Invariant·계약이 먼저**.  
- 여정: Invariant → 계약 → 도메인 분리 → **Dual-Track** RED→GREEN→REFACTOR → 회귀.  
- **UI+Logic 프레임으로 보면:** 성공은 “**UX Contract 문장**과 **Logic Rule 문장**이 시나리오마다 짝을 이루고, 테스트로 추적된다”는 것과 동일선상에 둘 수 있음.

## D. Logic 트랙 (Entity + Control + “계약 층 Algorithm 분리”)

### D-1. 불변조건 (§4)

- INV-01~10 표 전부 유지. Epic vs `02` INV 번호 비1:1 주의 문구 유지.

### D-2. 기능 요구 — Logic Rule 관점 (§5)

User Story를 **Logic Rule 언어**(허용/거부/반환/차단/계산/중단 등)로 읽으면 다음과 같이 매핑할 수 있음.

| Story | Logic Rule 요지 |
|--------|------------------|
| **US-01** | 잘못된 격자는 도메인으로 **통과시키지 않는다**(검증 **거부**·경계 **차단**). |
| **US-02** | 빈칸 좌표를 규칙대로 **반환**한다. |
| **US-03** | 누락 두 수를 **계산·반환**한다. |
| **US-04** | 완성 격자에 대해 마방진·순열을 **판정**(유효/무효). |
| **US-05** | 순·역 조합으로 해를 **탐색**하고, 성공 시 6원소·1-based 좌표로 **반환**; 실패 시 **NO_SOLUTION** 등 계약대로. |

**의존 순서:** US-01 → US-02/US-03 → US-04 → US-05 (유지).

### D-3. ECB·Dual-Track (기존 §6.1 재명명)

- **Entity:** 순수 규칙·불변.  
- **Control:** 유스케이스 흐름.  
- **Boundary:** 입출력·포맷·1차 검사 (UI가 생기면 **같은 Boundary**의 또 다른 표현이 됨).

**기존 “Track A / Track B”는 Logic 트랙 내부 이원화로 유지하는 것이 맞음.**

| 트랙 | 역할 | RED의 근거 |
|------|------|------------|
| **Track A (Contract)** | 입출력·예외·Invariant 일치 | 규칙·계약 — 알고리즘을 바꿔도 유지 |
| **Track B (Algorithm)** | 백트래킹·CSP 등 | 내부 전략 — 리팩터로 **바뀌어도 됨** |

### D-4. 핵심 I/O·에러 (§6.2)

- 입력/출력/에러코드/검증 순서/`MatrixRepository` InMemory — 그대로 **Logic·Boundary 계약**의 정본.

### D-5. 코드 품질 (§6.3)

- Python·Black·TDD 금지 사항·커버리지 — **Logic + 공통** 품질 바닥.

## E. UI 트랙 (Boundary / UX Contract)

**원문 PRD는 CLI를 Boundary로 두고 GUI는 Out of Scope**였음. Dual-Track **UI**로 정리하면 다음이 한 덩어리가 됨.

| 항목 | 내용 |
|------|------|
| **대상** | (현재) **CLI**: 표준 출력·표준 오류·종료 코드, 인자/파이프로 들어온 격자 표현. (확장 시) **Web/App**: 격자 입력, 에러 문구, “완료” 메시지, 로딩. |
| **UX Contract 언어** | 보인다/안 보인다, 가능/불가능, 활성/비활성, 포함/미포함 — **시나리오마다** Logic Rule과 **1:1 매핑 표**로 적는다(슬라이드 6.2 방식). |
| **RED** | “디자인(또는 CLI 계약)”으로 실패하는 테스트 — **로직의 내부 클래스를 직접 알 필요 없음**. |
| **독립성** | UI 테스트는 **렌더링/메시지/상태**만; Logic 테스트는 **격자·검증·해**만 — 서로 **모른다**. |
| **기존 US와의 연결** | US-01~05의 **AC**를 “사용자에게 어떤 피드백이 **가시적**이어야 하는가”로 풀면 **UI(또는 CLI) 시나리오**가 됨(예: 빈칸 개수 오류 시 **에러 문구 visible** = Logic에서 검색 **중단**). |

BDD Gherkin(§7)은 **UI 트랙**과 **Logic 트랙**을 잇는 **시나리오 공통어**로 두기에 적합하며, Given/When/Then이 **UX·Logic 매핑 표**의 시나리오 열과 대응시키기 좋음.

---

## F. MLOps (확장 시 · 현재 PRD와의 연결)

**지금 PRD 본문에는 “학습용 MLOps 제품” 요구가 없으므로**, 슬롯만 명확히 두는 정리가 됨.

| 구분 | Dual-Track + MLOps에서의 위치 |
|------|------------------------------|
| **Logic** | 모델 **입력/출력 스키마**, 전처리 **허용/거부**, 임계값, `NO_SOLUTION`과 유사한 **비즈니스 결정** — **Logic Rule·Contract 테스트**로 RED. |
| **MLOps** | 모델 **아티팩트 버전·해시**, 배포, 추론 **지연/가용성**, **스키마 계약** 검증, 드리프트·품질 **관측**(단위 테스트와 분리). |
| **UI** | 추론 결과·신뢰도·에러·재시도를 **UX Contract**로 고정; UI 테스트는 **API 목(mock)** 으로 Logic·MLOps를 대체 가능. |
| **비결정성** | Logic RED는 “동일 시드/고정 픽스처/스키마·임계값”에 걸고, **확률적 출력**은 별도 계약·모니터링. |

**현재 Magic Square만으로는** MLOps = “나중에 휴리스틱/추천/랭킹 ML을 붙일 때의 **원칙**” 정도로 두고, **필수 섹션은 아님**.

---

## G. 비기능·검증·이슈 (§8~§9)

- NFR 표, G1~G3, Sign-off — **Logic + 공통 품질** + (UI 도입 시) **E2E·접근성**을 NFR에 **추가**할 수 있음.

## 2. Logic 트랙 — 잘 맞는 부분

- **§4 Invariant, §5 User Stories, §6.2 계약**이 “Logic Rule + 입출력 계약”의 **정본** 역할을 한다.
- **§6.1 Track A (Contract) / Track B (Algorithm)**은 슬라이드의 “로직은 규칙으로 RED”와 **같은 층** 안에서의 **세분화**로 보면 **일관됨** (알고리즘을 바꿔도 Contract 테스트는 유지).
- **ECB**에서 `entity`·`control`·도메인 테스트는 **UI를 모른다**는 점(§6.1 의존성 규칙)은 Logic 트랙의 **검증 가능한 분리**와 잘 맞는다.
- **§7 Gherkin**은 Behavior를 한국어/영어 시나리오로 잡는 **시나리오 층**이 있어, 나중에 **“시나리오 | UX | Logic” 매핑 표**로 확장하기 좋다. 다만 **현재 Gherkin은 “부분 퍼즐 완성” 중심**이라, UI/CLI **표시**까지는 박혀 있지 않을 수 있음.

---

## 3. UI 트랙 — PRD에 있는 것과 부족한 것

**있는 것**

- **§2.1** `CLI` 등 **경계 입출력** In Scope.  
- **§6.1** `boundary` = CLI, 포맷, 1차 검사, 결과 직렬화.  
- **§6.2** 에러코드·검증 순서 = **사용자(또는 상위 시스템)에 돌려주는 계약**의 기반.  
- **§2.2** GUI / Web **Out of Scope** → “지금은 UI를 제품 경계의 주 언어로 쓰지 않는다”는 **명시적 선택**.

**부족한 것 (Dual-Track UI 기준으로 보면)**

- **UX Contract 어휘** (visible / active / error 메시지 포함 등) **정의 없음.**  
- **시나리오 ↔ “화면(또는 CLI)에서 무엇이 보이는가”**를 고정한 **3단 매핑 표** 없음. US AC는 **Logic·도메인**에 가깝다.  
- “**UI RED는 Logic을 모른다**”는 문장이 PRD에 **없다** (코드 구조는 ECB로 암시될 뿐).

→ 정리하면, **Boundary는 문서에 있으나, “UI 트랙 TDD”를 요구사항 수준에서 약속한 상태는 아니다.** 컨셉을 채택하려면 **§2 범위 갱신(GUI In) + 별절(UX Contract·매핑)** 이 필요하다.

## 4. MLOps

- **MLOps**에 해당하는 어휘(모델, 아티팩트, 드리프트, 파이프라인, **추론 SLO** 등)는 **PRD에 없다.**  
- `Report/02`에 **Data·Repository**는 있어도 **“학습·배포·모니터링”** 으로 읽히지 않는다.  
- 따라서 **“Dual-Track + MLOps” 전체**를 PRD에 반영하려면, **MLOps는 “현재 본 제품 = 비대상, 확장 시 §x에 넣는다”** 식의 **한 절**이라도 넣는 편이 컨셉과 **이름**이 맞다. 없으면 “MLOps”는 **이 문서 밖**의 이야기다.
