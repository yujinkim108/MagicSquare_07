## KPT 한눈에 이해

- **Keep**: 이번에 효과가 검증된 방식. 다음 사이클에서도 그대로 유지/확대할 것
- **Problem**: 반복적으로 병목을 만든 이슈. 원인과 영향이 확인된 개선 대상
- **Try**: 다음 사이클에서 실험할 실행 항목. 담당/기한/성공 기준까지 명시

## K - Keep (유지할 것)

### 1) 품질/개발 리듬

- TDD 사이클(`RED -> GREEN -> REFACTOR`)을 지켜 결함을 조기 발견하고 수정 범위를 줄였다.
- 리팩토링에서 기능 확장 욕심을 억제하고 공개 계약(반환 포맷, 예외 정책)을 유지해 회귀 리스크를 낮췄다.
- 리팩토링 전/후 동일 테스트를 검증해 "코드 변경"이 아닌 "행동 보존"을 증명하는 습관이 자리잡았다.

### 2) 아키텍처/코드 개선 방식

- ECB 경계(`boundary -> control -> entity`)를 지키며 변경 영향 범위를 통제했다.
- 중복 제거 원칙(공통 로직 헬퍼 분리, 배치 시도 흐름 공통화)을 일관되게 적용했다.
- 작은 단위 커밋과 빠른 피드백으로 리뷰어가 변경 의도를 파악하기 쉬웠다.

### 3) 협업/운영 습관

- 15분 Daily Standup으로 이슈를 조기 공유하고 컨텍스트 정렬 속도를 높였다.
- Prompting/Report 문서화로 작업 히스토리와 의사결정 근거(Traceability)를 확보했다.
- GUI MVP를 조기에 확인해 핵심 사용자 흐름 검증을 빠르게 수행했다.

---

## P - Problem (문제/개선 필요)

### 1) 테스트/품질 리스크

- 테스트 커버리지 60% 미달 구간이 존재해 회귀 방어력이 구간별로 불균형했다.
- 커버리지 수치가 높아도 입력 다양성(경계값/반례/조합 케이스)까지 자동 보장되지는 않았다.
- 인덱스/매핑 기반 로직은 오프바이원 실수가 조용히 숨어들 가능성이 있다.

### 2) 리뷰/협업 병목

- PR 리뷰가 48시간을 넘기며 대기 시간이 커졌고, 컨텍스트 스위칭 비용이 누적됐다.
- 커밋 메시지/PR 설명/보고서 형식이 팀원별로 달라 리뷰 효율이 떨어졌다.
- 한 번의 프롬프트에서 변경 범위가 커지면 리뷰 가능한 단위가 무너졌다.

### 3) 프롬프트/산출물 운영 문제

- 산출물 위치를 명시하지 않으면 구현 코드와 테스트 코드가 섞여 배치되는 문제가 있었다.
- Prompt/Report 저장은 유용하지만, "언제 자동 저장할지" 운영 규칙이 없으면 누락 가능성이 있다.
- 회고 액션이 선언형으로 끝나 담당자/기한/지표 없이 흐려지는 경우가 있었다.

---

## T - Try (다음 사이클 시도)

### 1) 즉시 적용할 운영 규칙

- Pair Programming을 주 2회(회당 60분)로 도입해 난이도 높은 로직의 초기 품질을 높인다.
- PR 리뷰 SLA를 24시간으로 명문화하고, 초과 시 백업 리뷰어를 자동 할당한다.
- DoD를 "테스트 통과 + 문서 업데이트 + 리뷰 체크리스트 완료"로 고정한다.

### 2) 자동화/게이트 강화

- CI 필수 체크에 `flake8`, `pytest -q`, `pytest --cov`를 추가한다.
- 커버리지 하한(예: `--cov-fail-under`)을 팀 합의 수치로 고정해 품질 기준을 시스템화한다.
- 로컬에서도 동일 품질 검증이 가능하도록 원커맨드 스크립트를 제공한다.

### 3) 프롬프트 표준화

- 반복 작업 프롬프트를 Skill/Rule로 고정한다(커밋/푸시/PR/보고서/테스트 실행 포함).
- 프롬프트에 산출물 위치를 필수 명시한다.
  - 구현 코드: `src/`
  - 테스트 코드: `tests/`
  - 프롬프트 히스토리: `Prompting/`
  - 결과 보고서: `Report/`
- 한 프롬프트당 목적 1개, 변경 파일 수 제한, 허용/금지 디렉터리를 명시한다.

### 4) 테스트 전략 보강

- 파라미터화 테스트로 표준/경계/반례 케이스를 확대한다.
- 공통화 함수(예: 배치 시도)의 실패 사유를 "배치 실패/판정 실패/성공"으로 분리 검증한다.
- 통합 테스트와 경계값 테스트의 스프린트 최소 목표 수량을 운영한다.

## 실행 우선순위 (이번 스프린트 제안)

- **P0 (이번 주):** PR SLA 24h 도입, CI에 `flake8` 게이트 추가, 커밋/PR 템플릿 통일
- **P1 (2주 내):** 미커버 구간 테스트 보강, Pair Programming 정례화, 프롬프트 산출물 위치 규칙 적용

## 이번 KPT의 핵심 결론

- 좋은 개발 습관(TDD, 경계 관리, 문서화)은 이미 확보됐다.
- 병목은 "리뷰 리드타임", "형식 불일치", "자동화 부족"에 집중된다.
- 다음 사이클 성패는 규칙을 개인 습관이 아닌 **시스템(CI/템플릿/운영 SLA)** 으로 고정하는지에 달려 있다.
